# GoreeCloud Privacy VPN

**Experimental Linux-first privacy VPN built on WireGuard.** This is a separate repository and product from GoreeCloud VPN (NetBird fork). Its first milestone is a **single-client, two-server configuration generator** with strict local key handling, outbound leak prevention, transit-only entry routing and optional WireGuard-over-TLS/WebSocket transport.

> **Not production-ready.** Configurations and unit tests do not establish runtime correctness, bypass resistance, DNS leak freedom, or anonymity. Deploy only to isolated test infrastructure with console recovery.

## Architecture

```text
Client (gpv0 10.77.1.2)
      |
      | WireGuard #1 (optionally wrapped in wstunnel/WSS)
      v
ENTRY VPS (gpe0 10.77.1.1)
      |
      | source-specific route + nftables anti-fallback
      | WireGuard #2 (gpt0 10.77.2.1)
      v
EXIT VPS (gpt0 10.77.2.2)
      |
      | nftables forward restrictions + IPv4 NAT
      v
Internet (exit VPS WAN)
```

The **entry** sees the client source IP and its decrypted IP packets before re-encryption for the second hop. The **exit** sees destination traffic and performs NAT. Neither multi-hop nor WSS is a substitute for HTTPS or an anonymity network. You must control **two independently addressed Linux hosts** for two-hop; placing both relay roles on one machine does not provide the intended host separation.

## Requirements

- Linux on client and both relays (Debian/Ubuntu recommended for development)
- Python 3.10+, `wireguard-tools`, `iproute2` and `nftables`
- A public IPv4 address per relay and firewall access to the selected ports
- Optional obfuscation: upstream `wstunnel`, a real TLS domain and a trusted matching certificate
- Out-of-band console or recovery access **before applying a firewall**
- All nodes run on separate hosts for meaningful relay separation

## Configure

Make a **private local** copy of `examples/topology.template.json` as `topology.json`. The sample addresses `203.0.113.10` and `198.51.100.20` are documentation addresses; replace them with real endpoint IPv4 addresses. Populate exactly four public keys. `topology.json` is gitignored by default.

On each relevant machine, generate a separate WireGuard private key **locally**:

```sh
umask 077
wg genkey > role.key
chmod 600 role.key
wg pubkey < role.key
```

Generate four separate keys total: **client**, **entry access**, **entry transit**, **exit transit**. Insert *only* the resulting public keys into your local topology. Do not share node private keys. Avoid collecting all four private keys on one machine. This initial format allows one client; additional peers require explicit changes and cannot be safely added by copy/paste.

On each host copy the shared public-only topology and the source code, then validate:

```sh
python3 -m privacyvpn validate topology.json
```

Render separately on each host (private output folders must be mode 0700):

```sh
# Client machine
python3 -m privacyvpn render client topology.json --key client.key --output ./generated-client

# Entry machine
python3 -m privacyvpn render entry topology.json --key entry.key --transit-key entry-transit.key --output ./generated-entry

# Exit machine
python3 -m privacyvpn render exit topology.json --key exit-transit.key --output ./generated-exit
```

Rendering **does not** change routes, interfaces, DNS or firewall. Files are created at mode 0600, and existing output files are never overwritten. Store artifacts on their respective hosts, outside public directories or source control.

## Deployment: isolated lab only

The sequence below describes the intended operator workflow; it has **not** been end-to-end validated on the GoreeCloud VPS. Review all generated files, choose WAN interface carefully and obtain console access before running commands. A mistake can sever SSH or all internet connectivity.

**Exit node:** Install `gpt0.conf` into `/etc/wireguard/` mode 0600. Ensure the underlay firewall admits the configured UDP transit port from the entry. Verify packet forwarding is appropriate for this isolated host. Load `exit-firewall.nft` first; enable `net.ipv4.ip_forward=1` by a scoped system configuration; then bring up `wg-quick up gpt0`. Use `nft -c -f exit-firewall.nft` to validate syntax when the host supports checking without applying.

**Entry node:** Install `gpe0.conf` and `gpt0.conf` mode 0600, and load `entry-firewall.nft` **before** allowing client traffic. Enable IPv4 forwarding, bring up `gpt0`, invoke `sh entry-routing-up.sh` exactly once, and bring up `gpe0`. Inspect the policy routing table and rule before accepting clients. Open the access UDP port only when using raw WireGuard; otherwise restrict raw UDP access and expose the designated WSS/TLS port. Server INPUT policy and host hardening are not automatically changed by this toolkit.

**Client:** Load `client-killswitch.nft` using `sudo nft -f client-killswitch.nft` **before** `wg-quick up gpv0`. This deliberately blocks non-VPN traffic, including direct IPv6 and LAN packets. It may prevent DHCP renewal, time sync, local discovery or captive-portal access. For WSS obfuscation, first follow the [underlay routing guide](docs/UNDERLAY.md), validate the pinned TLS hostname without DNS bootstrap leaks, and establish the entry-only underlay host route using the generated *operator-invoked* `client-underlay-route.sh`. With recovery access available, load the kill switch, then start `wstunnel-client.sh` before bringing up WireGuard. The routing helper is **not** invoked by the renderer or the WireGuard profile; no route is changed automatically.

Never paste real secret-bearing configs or shell transcripts containing private keys into GitHub issues, CI or support chats. The client kill switch and server transit filters are **not installed** automatically.

## Optional obfuscation

Set `transport` in your private topology to the structure in `examples/transport-wstunnel.json`. Use the **entry server** with a valid, trusted TLS certificate, and run its generated `wstunnel-server.sh CERT_PEM KEY_PEM` on a suitable network-accessible TLS port. It restricts forwarded packets to the local WireGuard UDP listener. On the client, the generated WireGuard endpoint changes to the local UDP forwarding port; the client WSS tunnel connects to the entry's TLS hostname. **The generated client explicitly adds `--tls-verify-certificate`: upstream wstunnel does not enable TLS peer verification by default.** Keep the option enabled, use a publicly trusted certificate matching the configured DNS hostname, and do not bypass verification with a self-signed/unknown certificate. Ensure the DNS name is securely mapped to the pinned IPv4 under the kill switch.

WSS/TCP introduces head-of-line blocking and may be worse on unstable networks. Operators should pin, verify and update the upstream wstunnel binary. This template does **not** claim censorship-proof or undetectable traffic, and no auto-failover or TLS lifecycle automation has been built yet.

Reference: [wstunnel upstream](https://github.com/erebe/wstunnel) and [wg-quick man page](https://man7.org/linux/man-pages/man8/wg-quick.8.html).

## Test / inspect

```sh
python3 -m compileall -q privacyvpn tests
python3 -m unittest discover -s tests -v
python3 -m privacyvpn --help
```

With temporary test keys, inspect the generated profiles, `wg show`, IP rule/route tables, DNS sources and active egress only in a disposable lab. A passing unit test or source review is **not** a verified privacy claim.

## Recovery

With out-of-band access: remove the VPN interface with `wg-quick down` (client gpv0; entry gpe0 then gpt0; exit gpt0); remove the entry routing rule using `sh entry-routing-down.sh`; remove only these project tables with `nft delete table inet gcvpn_client`, `nft delete table inet gcvpn_entry`, `nft delete table inet gcvpn_exit`, `nft delete table ip gcvpn_exit_nat` as appropriate. Verify the host's existing routing and network policy before re-enabling services. **Removing the client kill switch intentionally restores non-VPN egress**; only do so when you want to return to the underlay connection.
